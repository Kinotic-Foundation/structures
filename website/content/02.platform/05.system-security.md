## Overview

This page describes the architectural choices behind Kinotic's IAM. It is the *why*; for the operational *how* (signup flows, login flows, endpoint reference) see [Organization Management](/platform/organization-management), and for the layered enforcement applied to every request path see [Defense in Depth](/platform/defense-in-depth).

The platform supports email/password and OIDC authentication, isolates user pools by scope, stores credentials separately from user records, and uses standalone `OidcConfiguration` entities that are referenced (not embedded) by the scopes that consume them.

## Three Scope Layers

Every `ParticipantIdentity` carries its scope structurally, in two optional string fields — `organizationId` and `applicationId`. Which of them is set determines the layer: neither set → `SYSTEM`, `organizationId` only → `ORGANIZATION`, both set → `APPLICATION`.

| Layer | Scope fields | Who | Auth Path |
|---|---|---|---|
| **Organization** | `organizationId` set, `applicationId` null | Customer org admins and members | Email/password or OIDC (platform-social or per-org SSO) — see [Organization Management](/platform/organization-management) |
| **Application** | `organizationId` and `applicationId` both set | End-users of an application owned by an org | Email/password or OIDC — credentials and OIDC configs are scoped to the application |
| **System** | both null | Platform operators running the Kinotic servers | Email/password at the system server; planned to move to Microsoft Entra — see [System Authentication](/platform/organization-management#system-authentication) |

A user with email `jane@example.com` in Organization A is a fundamentally different identity from `jane@example.com` in Application B. They have separate `ParticipantIdentity` rows, separate `IdentityCredential` rows, and separate authentication paths. This prevents accidental cross-scope access and lets the same person have different authentication methods at different scopes (e.g. password at the org, federated SSO at one of the org's apps).

### How users are differentiated

A user's identity is determined by the combination of three values: **email + organizationId + applicationId**. The same email address can exist many times across the platform — each combination produces a completely separate user record with its own credentials, enabled state, and OIDC links.

For example, the same person could carry four distinct identities:

- A developer in their organization (org-A-id, no application)
- A test account in one of their applications (org-A-id + app-A-id)
- A customer end-user in a different application (org-A-id + app-B-id)
- A second org as the same person via social-OIDC (org-B-id, no application)

Each is a separate row. Disabling one does not disable the others. Authentication against one does not grant access to any of the others. Scope isolation is enforced at every lookup — there is no query that returns users across scopes.

For OIDC users, the platform additionally tracks `(oidcSubject, oidcConfigId)` so that one social identity can map to multiple `ParticipantIdentity` rows in different orgs. Social login resolves that pair to a single org user and takes the first match, so a person who joined two organizations with the same social identity lands in one of them without choosing.

### Why three layers

Two layers (platform vs tenant) would force organizations and their applications to share a user pool. That doesn't work because:

- An organization's developers should not automatically be end-users of every application they manage.
- Application end-users should not have access to organization-level tooling.
- Different applications under the same organization may serve completely different user populations.

Three layers map directly to real-world trust boundaries: the platform operator trusts the infrastructure, the organization trusts its developers, and the application trusts its users.

## Authentication Methods

Both methods are available at the Organization and Application layers:

- **Email/Password** — Credentials are verified against bcrypt hashes. Password hashes are stored in a separate `IdentityCredential` entity (a different Elasticsearch index) and are architecturally invisible to the rest of the system. User CRUD operations have no way to accidentally expose credentials.
- **OIDC** — JWT tokens are validated against the `OidcConfiguration` the target scope offers. The platform verifies signature, issuer, audience, and expiration via JWKS.

A browser authenticates over HTTP and carries a session cookie; the STOMP WebSocket upgrade reads the logged-in `Participant` back out of that session, so the browser never handles a token. Each login in the session is bound to the page that made it, and the upgrade reads the login of the page opening the socket (see [Defense in Depth](/platform/defense-in-depth#browser-sessions)). Scope is structural rather than header-supplied: an organization login establishes an `OrganizationParticipant`, an application login an `ApplicationParticipant`, and that participant type is what scopes the caller's authority for the rest of the connection. A non-browser client presents a Kinotic JWT instead, whose `organizationId` / `applicationId` claims carry the same scope. Each server names its session cookie `__Host-kinotic-<server>-session` (the management server's is `__Host-kinotic-management-session`) and keeps its sessions in a cluster map of its own, `<server>.vertx-web.sessions`, so a session one server issued is unknown to the others, even on a development machine where they share `localhost` and cookies ignore the port. Browsers accept a `__Host-` cookie only when it is Secure, scoped to path `/` and set without a `Domain`, so a page on a sibling host of the API, such as a published UI under the sites domain, can neither plant nor override it. The cookie is `SameSite=Lax`, which sends it from the API's own site, the one the sites domain shares with the application API hosts in production (`<app>--<ui>.<org>.kinotic.io` and `<org>--<app>.apps-api.kinotic.io`); `kinotic.apiGateway.sessionCookieSameSite: NONE` sends it from any origin the CORS pattern admits, for an environment whose published sites and API live on unrelated domains.

Each server authenticates only its own kind of caller. A client outside a browser presents a Kinotic access token (`Authorization: Bearer`), or a `clientId` and `clientSecret`: a user's email and password, checked in the scope the `organizationId` and `applicationId` headers select, or a machine's id and secret. The server resolves the identity the credentials prove and admits it only when it is one of its own; any other identity fails as invalid credentials, the same answer a wrong password gets:

| Server | Admits |
|---|---|
| org | An organization's users, the clients they have authorized, and its machines other than application runtimes (`OrganizationParticipant`) |
| system | Platform operators, the clients they have authorized, and the platform's machines such as the vm-manager (`SystemParticipant`) |
| app | An application's users, the clients they have authorized, and its machines (`ApplicationParticipant`), and the runtime workloads of an organization's applications (`OrganizationParticipant`); on an application's API host, only that application's identities and its organization's runtimes |

## OIDC Configuration

Provider configurations share a shape but not an owner. Every kind extends the sealed `OidcConfiguration` — `name`, `provider`, `clientId`, `authority`, `audience`, `enabled` — and is stored the way the kinds of `ParticipantIdentity` are: one index, `kinotic_oidc_configuration`, holding every kind as a polymorphic document whose persisted `type` discriminator selects the subtype it is read back as, each subtype carrying the fields only its owner has. The platform operator's registrations are the abstract `ManagedOidcConfiguration`, which carries the operator-only fields (`secretNameRef`, and the explicit endpoints `authorizationUri`, `tokenUri`, `userInfoUri`, `userEmailsUri`, `scopes` for a provider such as GitHub with no discovery document); its two concrete kinds differ in whom they sign in. An organization's own are the abstract `OwnedOidcConfiguration`, which carries the organization's fields (`organizationId`, `providerAccount`, `confidentialClient`, `createUserOnSignIn`); its concrete kinds differ in which of the organization's sign-in scopes offers them.

| Type | `type` | Owner | Lifecycle | Client secret |
|---|---|---|---|---|
| `OrgSignupOidcConfiguration` | `ORG_SIGNUP` | The platform operator, for organization users signing up and in; belongs to no organization | Seeded by SQL migration; saved by a system participant only | `secretNameRef` names one the operator placed in the platform's secret storage |
| `ApplicationSocialOidcConfiguration` | `APP_SOCIAL` | The platform operator, for the users of any organization's applications; belongs to no organization | Seeded by SQL migration; saved by a system participant only. Offered at an application's login when the application names the registration's provider kind in its `socialProviders` | `secretNameRef`, as above |
| `OrganizationOidcConfiguration` | `ORGANIZATION` | One organization (`organizationId`, enforced by `OidcConfigurationService` against the saving participant), for its own login | Managed by the owning org, which names its `providerAccount` at a provider kind offered to organizations; the `authority` is derived from the kind's template on every save | Held in the organization's scope of the secret storage, keyed by the configuration's id; the row's `confidentialClient` says one is held and nothing on it names it |
| `ApplicationOidcConfiguration` | `APPLICATION` | One organization, for the login of one of its applications (`applicationId`, held to the organization's own) | As above | As above |

Kinotic's own GitHub registration is an `OrgSignupOidcConfiguration` — it powers the "Continue with GitHub" button on org signup and org login, and belongs to no organization because signup happens before one exists. Kinotic's Google and Microsoft registrations are `ApplicationSocialOidcConfiguration`s: one registration per provider, which any application switches on by naming the provider kind in its `socialProviders`, so the application's users sign in with Google or Microsoft without the organization registering with either. A user who revokes the app's access at the provider revokes it for every application offering that registration, the trade one shared registration makes. Because the registration is shared and a provider returns only to a redirect URI registered in advance, its sign-ins return to the app server's own host rather than the application's API host, and the verified identity is handed to the application's host under a single-use code — see the app routes in [Organization Management](/platform/organization-management#endpoint-reference). Everything an organization configures for itself is the third kind.

### Why types rather than one with a flag

The difference between the kinds is *ownership* and *scope*, and those are exactly what must never be got wrong. The subtypes keep the fields apart: only a `ManagedOidcConfiguration` has a `secretNameRef`, so no row an organization can write has a field that names a platform secret, only an `OwnedOidcConfiguration` has an `organizationId`, and only an `ApplicationOidcConfiguration` has an `applicationId`, which is required rather than nullable because the kind is the scope. `OidcConfigurationService` holds every write to its kind's owner — a system participant for a managed registration, a participant of the named organization for an organization's, and for an application's kind an application of that organization — and its finders filter on the discriminator, so an org sign-up lookup never answers with an organization's SSO and an application's lookup never answers with the organization's portal SSO. A single type with an `isPlatform` boolean and nullable scope fields would put that guarantee back in the hands of every caller.

### One configuration, one scope

An organization's configuration is offered at exactly the scope its kind names and nowhere else: an `OrganizationOidcConfiguration` at the organization's own login, an `ApplicationOidcConfiguration` at that application's login. There is no sharing across scopes. An organization that uses one Okta application for its portal and for one of its own applications copies the configuration with `OidcConfigurationService.copy(sourceId, applicationId)`, which creates a configuration of the target scope's kind carrying the source's provider, account, client id and client secret, under an id of its own. Each copy therefore has its own callback URL, which the provider must be given, and a client secret the provider rotates is updated on each copy. That is the trade for every callback trusting only the row it loaded: the configuration says where it is offered, and nothing but the row decides what a sign-in through it may do.

Each owned configuration also decides, with `createUserOnSignIn`, what happens to an identity its provider verifies that no user of the scope is bound to: refused, or created as a user of the scope from the provider's verified email and name and bound to the identity. An email the scope already holds under another method is refused either way. Off by default.

### Resolving what a scope offers

`OidcConfigurationService.findEnabledForScope(organizationId, applicationId)` is the single answer to "which providers may this login page show", keyed on the same `(organizationId, applicationId)` pair the rest of the platform scopes by. The organization's own login offers the enabled org sign-up registrations followed by its enabled `OrganizationOidcConfiguration`s; an application's login offers its enabled `ApplicationOidcConfiguration`s followed by the platform's social registrations whose provider kinds the application's `socialProviders` names. The login, invite-accept, and signup pages all read it, so what a page renders and what its start endpoint accepts cannot drift apart. A sign-in start or callback that names a configuration asks `findOffered(configurationId, organizationId, applicationId)` the matching question for one configuration, so a configuration an organization owns at one scope cannot sign anyone in at another.

### Where client secrets live

Client secrets are never stored on a configuration row, and the kinds keep theirs apart, so a row an organization controls can never reach a secret of the platform's.

A managed registration's `secretNameRef` names a secret the operator placed in the platform's secret storage, which `SecretReferenceResolver` fetches at flow time — Azure Key Vault in a deployed environment, `KINOTIC_AKV_*` properties (environment variables or keys in any loaded config file) in development. Only `ManagedOidcConfiguration` has the field.

An `OwnedOidcConfiguration` has no secret name at all. Its secret is given to `OidcConfigurationService.save(configuration, clientSecret)`, which stores it through `SecretStorageService` in the organization's scope (`organizationId`), keyed by the configuration's id, and sets the row's `confidentialClient` to say a secret is held; `null` makes the configuration a public client, clears the flag and deletes the stored secret, and deleting the configuration deletes it too. A copy of a configuration stores the secret again under the copy's id. At flow time `OidcFlowOrchestrator` reads it back through `OidcConfigurationService.findClientSecret`, never through `SecretReferenceResolver`, and a public client's flag answers without a read of the secret storage. Because the secret is addressed by the owner and the row rather than by a name on the row, a configuration returned by any service carries nothing a client could use to find or name it, and `ApplicationService.getLoginProviders` answers with a `LoginProviderSummary` (id, name, provider kind, type) rather than the configuration at all.

### Where the server is willing to connect

An organization never names a URL. It chooses a provider kind that `OidcProviderKind.offeredToOrganizations()` admits and gives its account at that provider in the form the kind asks for: the directory (tenant) id for Entra, the Okta domain for Okta, nothing for Google. `OidcConfigurationService` fills the kind's issuer template with that account on every save and stores the result as the `authority`, replacing whatever was sent, and each kind's account pattern admits no scheme, port, path, userinfo or foreign host. So every host the sign-in flow fetches — the discovery document and JWKS at the authority, the token endpoint the discovery document names, and the identity endpoints — is one of the provider's own, and there is nothing an organization can point the server at. Kinds with no template, such as Keycloak or a generic OIDC server at a customer's own host, are not offered to organizations. The curated social rows are the operator's and may name endpoints explicitly.

The identity endpoints (`userInfoUri`, `userEmailsUri`) are fetched with no redirects followed. The deployment's egress policy denies the server pods the node's instance-metadata and WireServer addresses (see the terraform under `deployment/terraform/azure/cluster`), which is what protects the one kind of destination that answers a plain unauthenticated request with the node's own identity.

## Sign-Up

Self-service signup is wired up for the Organization scope. Both email/password and social-IdP entry points create the `Organization` together with the founding `ParticipantIdentity` — see [Organization Management](/platform/organization-management) for the step-by-step.

For the Application scope, end-user provisioning is admin-driven: an org admin (or the application's own admin tooling) creates `ParticipantIdentity` rows in the application's scope, or invites them — see [Organization Management](/platform/organization-management). There is no self-service sign-up form for an application scope. An application whose tenants the platform manages may instead let an `ApplicationOidcConfiguration` with `createUserOnSignIn` create a user on the first sign-in of an identity its provider verifies, which gives the new user a tenant of their own; under tenant administrators every user is created by an administrator or an invitation, since a user there is never without a tenant.

## Design Decisions

### Credential separation

Authentication secrets — user password hashes and machine client-secret hashes — are stored in a separate `IdentityCredential` entity, keyed by identity id and not exposed through any published service interface. The identity entity is part of the public API — returned by CRUD operations, displayed in UIs, passed around in service calls. Storing credentials separately means secret hashes are architecturally invisible to the rest of the system.

### Scope as string fields

The user entity stores `organizationId` and `applicationId` as plain string fields rather than typed references, and the layer is read structurally from which ids are set. This avoids coupling `ParticipantIdentity` to `Organization`/`Application`, keeps queries simple (term filters on keyword fields), and lets the scope model evolve without migrating user records.

### Single identity entity for all scopes

All three scope layers share the same `ParticipantIdentity` hierarchy, distinguished by the scope fields. Separate types per scope would triple the service interfaces and implementations with no behavioral difference — the authentication logic is identical across scopes.

### Users, delegates, and machines

A `ParticipantIdentity` is a person (`UserParticipantIdentity`), a client a person has authorized to act on their behalf (`DelegatingParticipantIdentity`) — the Kinotic CLI via the device-code grant, or an MCP host such as an LLM assistant via the PKCE authorization-code grant — or a non-human caller with its own credential (`MachineParticipantIdentity`), such as a platform daemon or an external client of an organization's application API. A delegate carries its owner's exact scope, is unique per `(owner, client)` — approving the same client twice reuses one delegate, each approval issuing a fresh refresh-token lineage under it — and authenticates only with Kinotic-issued tokens whose `sub` is the delegate's own id, so every request records *which client* acted, not just whose authority it used.

Both grants are bound to the server that started them. The authorization request and the device-code flow record the OAuth issuer of the server whose endpoint began them, and on the app server each application's API host is an issuer of its own; only that issuer's token endpoint redeems the code: an authorization code presented to another server's or another application's token endpoint is refused and burned, and a device code polled there reads as unknown.

Revocation follows from the model: authentication re-reads the identity on every token validation, so disabling a delegate cuts that client off on its next request even if its access token has not expired, and a delegate authenticates only while its owner is enabled — disabling a user revokes every client authorized on their behalf with no cascade to miss. Deleting a user deletes their delegates outright.

Each approval issues a refresh-token lineage under the delegate — a *session*, labeled with the device name the client supplied (the CLI sends one with `device_name` on the device-authorization request). The published `DelegateService` gives the signed-in user their own delegates and sessions — list them, end a single session, or revoke a delegate entirely. Alongside it, `ProfileService` reads and writes the caller's own identity: `findMyProfile` returns it and `updateDisplayName` sets the name shown wherever they appear. Both services address the calling user rather than taking an id, and admit only a person — a delegate cannot read or edit the account that authorized it. The portal surfaces them as the **Profile** and **Connected apps** pages under the account menu. Because `DelegateService` keys on the calling participant alone, it serves each scope its servers admit: the system console carries the same **Connected apps** page under its account menu, so a platform operator revokes the clients authorized on their own account there. It is a `management-api` service, which the app server neither hosts nor reaches, so an application's users have no listing or revocation of the clients the app server authorizes on their behalf.

### Machine identities

A machine connects the same way every Kinotic client does — over the STOMP gateway, authenticated by credentials on the WebSocket upgrade: its identity id as `clientId` and the secret issued at provisioning as `clientSecret`. A `clientId` containing `@` is a user email; anything else resolves only to a `MachineParticipantIdentity`, so a user's id and password can never authenticate as a machine. The machine's scope comes structurally from its own identity — no scope headers needed. There is no token to manage: the client library owns connect and reconnect, re-presenting the same static credentials, so any crash or restart self-heals.

```typescript
await Kinotic.connect({server: {host, port}, credentials: new BasicCredentialsResolver(machineId, machineSecret)})
```

Provisioning generates the secret — it is returned in plaintext exactly once and stored only as a hash, in the same credential store that holds user password hashes. The secret is verified on every handshake, so disabling the machine identity cuts it off on its next connection, and rotating the secret invalidates the old one immediately.

Every machine carries a `machineKind`, set when it is provisioned, naming what its credential is for:

| `machineKind` | Scope | Provisioned by |
|---|---|---|
| `CLIENT` | SYSTEM: a platform daemon such as the vm-manager | the system console, through `SystemMemberService` |
| `CLIENT` | APPLICATION: an API client of one application, acting with that application's scope, exactly the position an application end-user occupies | an org member, through `MachineService` |
| `PROJECT_SYNC` | ORGANIZATION: a project deployment's sync workload | the deployment |
| `APP_RUNTIME` | ORGANIZATION: the runtime workload of one of a project's microservices | the deployment |

Org members manage the machines of their applications through the published `MachineService` — create (disclosing the generated secret once), list, rotate the secret, disable/enable, and remove — surfaced in the SPA as the **Machines** page under each application. Every operation proves the application belongs to the caller's organization; machines of other organizations are invisible.

SYSTEM-scope machines are the platform's own, so they are managed from the system console instead, at **Members → Machines**, through `SystemMemberService` in the system zone. It carries the same lifecycle as `MachineService` under the same method names — create, list, rotate the secret, disable/enable, and remove — so each console's **Machines** page is the same `MachinesTable` component, bound to whichever service owns the scope it lists. The page is how a worker node's vm-manager gets the `KINOTIC_CLIENT_ID` and `KINOTIC_CLIENT_SECRET` it connects with. `SystemMemberService` works on SYSTEM scope alone: an organization's machines are not reachable from it even though a SYSTEM participant may address it.

### Multi-org identity keyed by `(oidcSubject, oidcConfigId)`

For OIDC users, identity across org-scoped `ParticipantIdentity` rows is keyed by the OIDC `sub` claim plus the configId — **not** email. Email is mutable at the IdP and the same email across two IdP tenants is two different people. The `sub` is stable within an issuer, and pairing it with the configId disambiguates issuers.

### Auto-derived organization id

The `Organization.id` is derived from the user-supplied name (slugified) at signup time. This supports subdomain-based tenant identification (e.g. `customer.kinotic.ai`) without surfacing UUIDs in URLs. The id `xn` is reserved: an application's host labels begin with `<organizationId>--`, and DNS reserves labels beginning `xn--` for internationalized names.

### Client identity is a domain, not a string

MCP hosts identify themselves with an [OAuth Client ID Metadata Document](https://datatracker.ietf.org/doc/html/draft-ietf-oauth-client-id-metadata-document-01): the `client_id` is an HTTPS URL, and the gateway fetches the JSON document it names on each authorization request (cached for `kinotic.domain.oauth.clientMetadataCacheTtl`). The document registers the client's `redirect_uris` and `client_name`.

The security property is that the client had to control that host to serve the document there, so the consent page displays the `client_id` host alongside the claimed name — a client cannot present itself as `claude.ai` without owning `claude.ai`. The page also names the account the approval would bind to: the login the browser session holds for the consent page's own origin. A system-scoped session carries no organization, so a delegate approved under it reaches every organization's MCP tools; the page warns about that before the operator approves. Under the dynamic registration this replaces, `client_name` was self-asserted by whoever called the registration endpoint.

Validation, per the draft: the URL must be `https` with a path component and no fragment, userinfo, or dot segments (§3); the host must not resolve to a special-use address (§6.5); the fetch must answer `200` with no redirects followed (§4) and stay under `clientMetadataMaxBytes` (§6.6); and the document must name its own URL as `client_id` and carry no client secret (§4.1). Failures abort the authorization request and are never cached (§4.3, §4.4).

`kinotic.domain.oauth.allowedClientIds` lists the document URLs that may start a flow, and is required — a deployment names the clients it accepts or fails to start. A `client_id` that is not listed is rejected, so clients are onboarded explicitly, the deployment pattern of §6.10. A host that validates against the rules above still needs its document URL added before it can connect.

Each Anthropic surface presents its own document URL, and the servers ship both:

| Client | `client_id` |
| --- | --- |
| Claude Code | `https://claude.ai/oauth/claude-code-client-metadata` |
| Claude web, desktop, and mobile custom connectors | `https://claude.ai/oauth/mcp-oauth-client-metadata` |

## Bootstrap

`kinotic-migration` runs to completion before the servers start. Migrations are versioned SQL applied once per version: `V1__init.sql` creates the Elasticsearch indices and seeds the curated social providers into `kinotic_oidc_configuration` as `ORG_SIGNUP` rows. A migration whose filename carries environment suffixes — `V2__kinotic_test_users.development.test.sql` — is applied only in those environments, which is how test fixtures stay out of production.

There is no startup bootstrap step for OIDC. A seeded provider row carries only a `secretNameRef`; the client secret itself is placed in external secret storage by the operator and read at flow time, so no secret passes through a migration or a config file.

## Network Security

- All client-to-server communication occurs over WebSocket with TLS in any non-local environment.
- Each server's api-gateway port (default org `58503`, system `58504`, app `58505`) carries the auth REST endpoints on `/api/*` and STOMP/WebSocket on `/api/v1`; the OAuth discovery documents stay at the root under `/.well-known/`. A later generation of the client protocol would be served at `/api/v2` beside the first, while the auth routes and their registered callback URLs never move.
- TLS terminates in each server's gateway (KinD: an mkcert certificate; Azure: a cert-manager certificate, behind a layer-4 LoadBalancer; the development server: a certificate per server, behind an SNI edge that passes TLS through unopened).

## What This Design Does Not Cover

- **Authorization** — Roles and policies. The authenticated session currently carries an empty roles list; future work populates it from the policy system.
- **Groups** — Group entities and membership management.
- **System-scope OIDC** — Platform operators do not authenticate through any of the OIDC flows above. Their sign-in to the system console, planned to move to Microsoft Entra, is a separate thing from how organization users sign up and in, and will be its own kind of `OidcConfiguration` beside the two above rather than a reuse of `OrgSignupOidcConfiguration` (deferred).
- **Account linking** — Linking an existing local account to a social identity is on the roadmap but not built.
